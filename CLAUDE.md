## Aperçu du projet

JOEM ("Job Offer & Employment Madagascar") est une application Flutter ciblant le marché de l'emploi malgache, mettant en relation recruteurs et chercheurs d'emploi. Le flux complet onboarding → inscription → connexion → dashboard est câblé de bout en bout, avec une vraie persistance locale (SQLite via `sqflite`/`sqflite_common_ffi`, voir `lib/core/database/app_database.dart` — comptes, offres, candidatures, notifications, historique de recherche : plus un simple mock en mémoire). Pas de state management (pas de provider/riverpod/bloc), pas de routeur déclaratif — uniquement `Navigator.push`/`pushReplacement`. Une seule paire de dashboards existe désormais (l'ancienne branche parallèle non branchée a été supprimée, voir plus bas). L'app reste presque entièrement locale, à une exception près : la connexion/inscription via Google (`GoogleAuthService`, package `google_sign_in`) contacte réellement les serveurs Google — c'est la seule fonctionnalité réseau de toute l'app, tout le reste (comptes, offres, candidatures, notifications, recherche...) reste 100% SQLite sur l'appareil. Côté recruteur, tout le dashboard est désormais réel (offres, candidatures par offre, vues, entretiens — tables `job_offer_views` et `interviews` ajoutées) ; côté candidat, "Mes prochains entretiens" et "Réponses reçues" restent volontairement mockés faute de table correspondante — voir "Ce qui reste à faire".

## Commandes

```bash
flutter pub get                     # installer les dépendances
flutter run                         # lancer sur un appareil/émulateur connecté
flutter run -d chrome                # lancer dans un navigateur (la cible web est configurée)
flutter test                        # lancer tous les tests
flutter test test/widget_test.dart  # lancer un seul fichier de test
flutter test --plain-name "Welcome screen loads"  # lancer un seul test par son nom
flutter analyze                     # analyse statique (utilise flutter_lints, voir analysis_options.yaml)
flutter build apk / ios / web       # builds par plateforme
```

Il n'y a pas de configuration CI, pas de règles de lint personnalisées au-delà de l'ensemble par défaut `flutter_lints`, et pas d'étape de génération de code (pas de `build_runner`). `pubspec.yaml` déclare, en plus de `cupertino_icons`/`google_fonts` : `image_picker` (photo de couverture/profil/logo — désormais toutes les deux persistées, voir plus bas), `file_picker`/`open_file` (CV), `sqflite`/`sqflite_common_ffi`/`sqflite_common_ffi_web`/`sqlite3_flutter_libs`/`path`/`path_provider`/`crypto` — la vraie base SQLite locale (`lib/core/database/app_database.dart`, un seul fichier `joem.db`, schéma version 24, migrations versionnées dans `onUpgrade`) qui persiste comptes, offres, candidatures, notifications et historique de recherche — `google_sign_in` (v7, API Credential Manager) pour la connexion/inscription Google réelle (`lib/core/services/google_auth_service.dart`), et `url_launcher` (composeur `tel:` / client mail `mailto:` — coordonnées cliquables du candidat dans `CandidateApplicationDetailScreen`). Aucune lib de state management (provider/riverpod/bloc) ni de routeur (go_router) n'a été ajoutée. `image_picker` nécessite les entrées `NSCameraUsageDescription`/`NSPhotoLibraryUsageDescription` dans `ios/Runner/Info.plist` (déjà ajoutées) ; Android nécessite la permission `INTERNET` dans `AndroidManifest.xml` (ajoutée avec Google Sign-In) et deux `<intent>` dans `<queries>` pour `url_launcher` (`DIAL` scheme `tel`, `SENDTO` scheme `mailto`).

**Config Google Sign-In requise avant de tester la connexion Google** : `lib/core/constants/google_config.dart` contient un `kGoogleServerClientId` placeholder (`'REMPLACE_MOI.apps.googleusercontent.com'`) à remplacer par le Client ID d'un client OAuth "Web application" créé sur Google Cloud Console, dans le même projet qu'un client OAuth "Android" (package `com.example.joem` + SHA-1 de signature). Sans ça, `GoogleAuthService.signIn()` échoue avec une `GoogleSignInException` de configuration. Voir le code de `google_auth_service.dart` pour le détail du flux (API `GoogleSignIn.instance`, pas l'ancienne API `GoogleSignIn()`).

**Problème d'environnement connu (Android)** : `flutter build apk`/`flutter run` sur Android échoue actuellement dans cet environnement avec `Error when reading '/main.dart'` pendant la tâche Gradle `compileFlutterBuildDebug` — confirmé pré-existant (reproductible même sur un `git stash` complet, donc indépendant de tout changement applicatif récent). À diagnostiquer séparément (config Gradle/Windows) avant de pouvoir tester Google Sign-In ou toute autre fonctionnalité sur un vrai appareil/émulateur Android depuis cette machine. `flutter build web` et `flutter analyze`/`flutter test`, eux, fonctionnent normalement.

## Architecture

Le code suit une structure **feature-first** sous `lib/` :

- `lib/core/` — briques partagées entre toutes les fonctionnalités :
  - `theme/` — tokens de design : `app_colors.dart`, `app_spacing.dart`, `app_durations.dart`, `app_shadows.dart`, `app_radius.dart`, `app_typography.dart` (échelles Poppins/Inter via Google Fonts — fusion de l'ancien `app_text_styles.dart`, supprimé), et `app_theme.dart` (le `ThemeData` Material 3 global, toujours *non* appliqué — voir ci-dessous). Les anciens doublons `app_radii.dart` et `app_text_styles.dart` ont été supprimés/fusionnés dans `app_radius.dart`/`app_typography.dart` : un seul fichier par token désormais.
  - `widgets/` — composants partagés : `glass_container.dart`/`glass_button.dart` (verre dépoli — `GlassButton` accepte un paramètre optionnel `color` pour surcharger le mauve `AppColors.primary` par défaut ; login et les wizards d'inscription lui passent `OnboardingColors.violet`), le kit de formulaire clair (`form_surface.dart`, `light_text_field.dart`, `light_dropdown.dart`, `joem_gradient_logo.dart`, `google_sign_in_button.dart`, `or_divider.dart`), le kit d'inscription en wizard (`registration_stepper.dart`, `wizard_navigation.dart`, `step_one_account.dart` — désormais un `StatefulWidget` qui déclenche une vraie authentification Google au tap, voir plus bas), `notification_badge.dart` (pastille rouge de compteur style Facebook, réutilisée par les headers et les nav basses des deux dashboards) et `profile_photo_viewer_screen.dart` (`ProfilePhotoViewerScreen` — visionneuse plein écran zoomable d'une photo, partagée par `JobProfileScreen` et `ProfileSidePanel`). Le "kit dashboard" (`dashboard_card.dart`, `section_header.dart`, `advice_card.dart`, `mini_line_chart_painter.dart`) a été supprimé : il n'était utilisé que par la branche dashboard non branchée, elle-même supprimée (voir "Ce qui a changé récemment"). `centered_logo.dart` (ancien wordmark en image PNG) a lui aussi été supprimé ; `joem_gradient_logo.dart` (`JoemGradientLogo`) le remplace partout — un texte "JOEM" au dégradé navy→violet (`ShaderMask` + Google Fonts Poppins), même identité que le bloc de marque du welcome screen.
  - `services/auth_service.dart` — service d'authentification utilisé par l'écran de connexion et les dashboards : 2 comptes de démo en dur (`employeur@gmail.com` / `candidat@gmail.com`, id négatif, aucune ligne dans `users`) + tout compte réellement inscrit (lu depuis SQLite). Méthodes `login()`, `logout()`, `restoreSession()` (reconnexion auto au démarrage), `isEmployer()`, `isJobSeeker()`, `setSession()` (ouvre une session juste après inscription), `loginWithGoogle()` (connecte un compte JOEM existant dont l'email correspond à celui du compte Google authentifié — ne crée jamais de compte, renvoie `null` si annulé par l'utilisateur ou `false` si aucun compte JOEM ne correspond), `resetPassword()` (réinitialisation locale du mot de passe par email, utilisée par `ForgotPasswordScreen` — pas de comptes de démo), `updateProfilePhoto`/`updateCoverPhoto`/`updateCv`/`updateJobSeekerProfile`/`updateEmployerProfile`/`addExperience`/`deleteExperienceAt` (persistent les modifications faites depuis `JobProfileScreen`/`EmployerProfileScreen` et leurs écrans "Modifier le profil").
  - `services/google_auth_service.dart` — fin enrobage de `GoogleSignIn.instance` (package `google_sign_in` v7, API Credential Manager sur Android) : `signIn()` ouvre le sélecteur de compte Google et renvoie un `GoogleSignInAccount?` (email/nom/photo), utilisé à la fois par `AuthService.loginWithGoogle()` (connexion) et `StepOneAccount` (inscription, préremplit email/nom/prénom).
  - `database/app_database.dart` — base SQLite locale unique (`joem.db`, schéma version 24, migrations versionnées dans `onUpgrade`, `sqflite`/`sqflite_common_ffi` selon la plateforme). Toutes les données réelles de l'app (comptes, offres, candidatures, notifications, historique de recherche) y vivent — voir "Ce qui est déjà fait" pour le détail par repository. Migration v13→v14 : ajout de `cover_photo` (BLOB) sur `job_seeker_profiles` et `employer_profiles` pour persister la photo de couverture du profil (auparavant perdue à chaque fermeture d'écran). Migrations v22→v23 : colonnes de réglages `EmployerSettingsScreen` sur `employer_profiles` — v22 `notifications_actives`/`entreprise_visible`/`publicite_personnalisee`/`communications_marketing`, v23 `mode_nuit`/`texte_agrandi`/`animations_reduites` (section "Affichage", miroir de `job_seeker_profiles`). Migration v23→v24 : table `job_seeker_profile_views` (une ligne par recruteur distinct qui ouvre `CandidateProfileViewScreen`, `UNIQUE(profile_user_id, viewer_user_id)`) — alimente le compteur "N vues du profil" de `JobProfileScreen`.
  - `constants/` — listes de référence partagées : `malagasy_cities.dart` (autocomplétion de localisation), `job_categories.dart` (`kJobCategories`, les 18 secteurs proposés à l'inscription recruteur et réutilisés pour filtrer les offres côté candidat), et `google_config.dart` (`kGoogleServerClientId`, à remplacer par un vrai Client ID OAuth avant de tester la connexion Google — voir "Commandes").
  - `utils/responsive.dart` — breakpoints partagés (`isTablet`/`isDesktop`).
- `lib/features/<feature>/presentation/` — chaque fonctionnalité possède ses écrans sous `presentation/` (sous-dossier `widgets/` pour les composants propres à l'écran). Fonctionnalités existantes : `welcome/`, `recruiter_registration/`, `job_seeker_registration/`, `login/` (dont `forgot_password_screen.dart`, voir plus bas), `dashboard/`.

Convention d'imports : dans les widgets propres à une fonctionnalité, les imports relatifs vers `core` sont parfois utilisés (ex. `../../../../core/theme/app_colors.dart`), parfois la forme absolue `package:joem/...` — les deux styles coexistent selon le fichier/la session qui l'a écrit ; jamais harmonisé.

### Point d'entrée et incohérence de thème

`lib/main.dart` construit toujours `MaterialApp` avec un `ThemeData` **inline** (sombre, Material 3, dérivé d'un `seedColor`, avec des personnalisations — coins arrondis des boutons/cartes, splash transparent) plutôt que d'utiliser `AppTheme.dark` défini dans `lib/core/theme/app_theme.dart`. `home` passe par `SplashScreen` (`lib/features/splash/`) avant `WelcomeScreen`. Remplacer ce thème inline par `AppTheme.dark` a été délibérément écarté (pas juste "pas encore fait") : `AppTheme.dark` n'a pas ces personnalisations, le switch ferait donc régresser visuellement les boutons/cartes/splash pour un gain purement cosmétique — à ne faire que si `AppTheme.dark` est d'abord complété pour matcher l'existant.

Les deux wizards d'inscription créent un vrai compte utilisable, que ce soit par email/mot de passe ou via Google : `LoginScreen` accepte aussi bien les comptes de démo codés en dur dans `AuthService` qu'un compte inscrit via `RecruiterRegistrationScreen`/`JobSeekerRegistrationScreen` (persisté en SQLite) — s'inscrire puis se reconnecter (au clavier ou via Google si l'inscription s'est faite via Google) fonctionne. Un compte créé via Google n'a pas de mot de passe connu de l'utilisateur (un mot de passe aléatoire est généré côté serveur) : `AuthService.resetPassword` (via `ForgotPasswordScreen`) reste le seul moyen d'en obtenir un s'il veut un accès classique en secours.

Dans `JobSeekerDashboard`, seuls les items "Recherche" (index 1), "Publier" (index 2), "Notifications" (index 3) et "Profil" (index 4) du menu bas naviguent réellement (`Navigator.push` vers un écran dédié, `lib/features/dashboard/presentation/pages/`) ; "Accueil" et "Favoris" ne font que changer l'icône active sans changer le contenu affiché.

### Recherche de comptes et profils consultables (candidat ↔ recruteur)

`AccountSearchRepository` (`lib/features/dashboard/data/account_search_repository.dart`) fait une recherche réelle en base, jamais de données mockées : `searchJobSeekers`/`searchEmployers` interrogent `job_seeker_profiles`/`employer_profiles` (+ compétences/expériences pour un candidat), "Aucun résultat" si rien ne correspond. L'historique de recherche (`search_history`, propre à chaque utilisateur et type de recherche) est enregistré à la fois sur validation clavier (`onSubmitted`) et à l'ouverture d'un profil depuis les résultats — sans ce second point, une recherche jamais "validée" au clavier avant de cliquer un résultat ne laissait aucune trace.

- `CandidateSearchScreen` (recruteur cherche un candidat) et `JobSearchScreen` (candidat cherche une entreprise) partagent la même structure : barre de recherche + historique, résultats sous forme de cartes. Aucun filtre au-delà du texte saisi (`showFilterButton: false` sur `SearchBarWidget`) — un filtre par localisation a été prototypé puis retiré à la demande, pas de trace dans le code actuel.
- Taper un résultat ouvre une vraie page de profil en lecture seule, pas une simple bottom sheet : `CandidateProfileViewScreen` (même identité visuelle que `JobProfileScreen` — bannière, avatar, "À propos", "Expérience", "Compétences", "Coordonnées") et `CompanyProfileViewScreen` (même identité que `EmployerProfileScreen`), tous deux dans `lib/features/dashboard/presentation/pages/`.
- `EmployerDashboard` appelle `AccountSearchRepository.fetchAllJobSeekers()` pour "Candidats suggérés" : tous les candidats inscrits (profil visible), classés par correspondance locale (titre/compétences/localisation vs mots significatifs des titres d'offres publiées), les non-matchés en fin de liste sans score.

### Doublon de palette à surveiller

Les dashboards restent sur `AppColors.primary` (mauve `0xFFA855F7`, `lib/core/theme/app_colors.dart`), tandis que login + les deux wizards d'inscription (et les widgets `core/widgets/` qu'ils partagent — `LightTextField`, `RegistrationStepper`, `WizardNavigation`, `StepOneAccount`, `JoemGradientLogo`, `GlassButton` via son paramètre `color`) utilisent `OnboardingColors.violet`/`navy` (`lib/features/welcome/presentation/welcome_palette.dart`, la palette du welcome screen). Ces widgets `core/widgets/` importent donc un fichier de `features/welcome/` — dépendance inversée à noter si `OnboardingColors` est un jour déplacé/renommé. Les écrans dashboard eux-mêmes (`employer_dashboard.dart`/`job_seeker_dashboard.dart`) n'ont pas été retouchés (toujours `AppColors`), mais une bonne partie de leurs sous-écrans est déjà passée à `OnboardingColors.violet`/`lavender` (recherche de comptes, profils consultables, écrans "Modifier le profil", `JobProfileScreen`/`EmployerProfileScreen`, `ForgotPasswordScreen`) — le doublon de palette traverse donc aussi les dashboards eux-mêmes selon l'écran. Non résolu, changer ça est un gros chantier visuel volontairement laissé de côté (voir "Ce qui reste à faire").

### Écran d'accueil (welcome)

`lib/features/welcome/presentation/welcome_screen.dart` est un `StatefulWidget` avec un `AnimationController` (900ms, `easeOutCubic`) pilotant le fondu d'apparition du contenu. Fond en dégradé `OnboardingColors.bgTop → bgBottom` (défini dans `welcome_palette.dart`) avec des vagues violettes décoratives peintes en arrière-plan (`_BottomWavesPainter`). Layout à hauteur fixe, sans scroll, chaque bloc dimensionné en fraction de la hauteur disponible (`OnboardingLayout`) via `LayoutBuilder`, avec un facteur `scale` global (borné 0.82–1.12) qui adapte la typographie à la hauteur utile réelle : `_HeroSection` (image hero) → `_BrandBlock` (wordmark "JOEM" en dégradé navy→violet via `ShaderMask`, grilles de points décoratives, baseline "Job • Offres • ...") → `_TitleBlock` (les deux `_ActionCard` "Je suis recruteur" / "Je cherche un emploi") → `_Divider` → `_DescriptionBlock` → footer "Se connecter" (`_LoginFooter`).

Chaque `_ActionCard` affiche un titre (`_AutoFitText`, taille de base `19 * scale`, jusqu'à 2 lignes, rétrécit automatiquement plutôt que de déborder) et un sous-titre à deux lignes qui défilent en boucle façon ticker (`_RotatingSubtitle`, taille de base `12 * scale`, `maxLines: 1` — chaque ligne est donc forcée sur une seule ligne, `_AutoFitText` réduit la police jusqu'à ce qu'elle tienne plutôt que de passer à la ligne). Textes actuels : recruteur → "Publier des offres et trouvez" / "les meilleur talent" ; chercheur d'emploi → "Trouvez l'opportunité qui correspond" / "à votre profil". `_ActionCard` garde délibérément son propre effet de carte (fond blanc, ombre violette) plutôt que `core/widgets/glass_container.dart` — ce n'est pas un composant nommé `RoleSelectionCardWidget` séparé, ce nom ne correspond à rien dans le code actuel.

### Ce qu'on trouve dans les dashboards

Espace Employeur — `lib/features/dashboard/presentation/pages/employer_dashboard.dart` :
- En-tête `EmployerHeader` (logo/initiale, notification avec pastille réelle — `countUnreadApplicationNotificationsForEmployer` — barre de recherche en lecture seule qui ouvre `CandidateSearchScreen`) + `EmployerProfileSidePanel` (logo, nom entreprise, stats, carte "Profil complété" tapable → `EmployerProfileScreen`).
- Bouton "Publier une offre" → `JobOfferPublishScreen` (formulaire réel : titre, description, localisation, salaire, type de contrat, affiche facultative), pas un composeur de post social.
- Grille de KPI "Tableau de bord" : **les 4 cartes sont réelles et cliquables** (`StatCard` a un `onTap`) — "Offres actives" = `_postedOffers.length` → `EmployerOffersScreen` ; "Candidatures" = `countApplicantsForEmployer` → `EmployerNotificationsScreen` ; "Entretiens" = entretiens à venir (`InterviewRepository.fetchUpcomingForEmployer`) → `EmployerInterviewsScreen` (tous les entretiens, badge "Passé"/"Modifié", tap → candidature liée) ; "Vues totales" = `JobOfferRepository.countOfferViewsForEmployer` (`job_offer_views`) → `EmployerOfferViewsScreen` (qui a vu quelle offre, `fetchOfferViewsForEmployer`). Les 2 nouveaux écrans sont dans `employer_stats_screens.dart`. Le bloc "Les Statistiques" du `EmployerProfileSidePanel` pointe sur les **mêmes 4 chiffres réels et écrans** (ancienne carte "Recrutements" mockée remplacée par "Vues totales").
- Carte "Entretiens du jour" : **désormais réelle** (`interviews` via `InterviewRepository`). Affiche les entretiens planifiés aujourd'hui ; s'il n'y en a aucun, bascule sur "Mes prochains entretiens" (3 plus proches à venir) ; message si rien. "Voir" sur une carte rouvre `CandidateApplicationDetailScreen` de la candidature liée. Les entretiens se créent depuis `CandidateApplicationDetailScreen` → bouton "Planifier un entretien" → `ScheduleInterviewScreen` (date, heure, présentiel/visio, lieu/lien, notes).
- **Notification côté candidat** : dès qu'un recruteur planifie un entretien, le candidat voit une notification "Proposition d'entretien" dans `JobNotificationsScreen` (fusionnée avec les notifications d'offres, triée par date), avec date/heure/lieu en aperçu ; tap → `CandidateInterviewDetailScreen` (récap complet en lecture seule). Si le recruteur **modifie** ensuite l'entretien (`ScheduleInterviewScreen` en re-planification), `InterviewRepository.update` incrémente `interviews.revision` et repositionne `interviews.notified_at` : la même notification repasse en non-lue, se re-libelle "**Entretien modifié**" (icône ambre, message qui invite à revérifier date/heure/lieu) et **remonte en tête** de la liste (tri sur `notified_at`). L'état lu/supprimé vit sur `interviews.seeker_read`/`seeker_deleted` (migrations v20/v21). Ces notifications comptent toujours dans la pastille du dashboard candidat, même si "Nouvelles offres" est désactivé dans les réglages (invitation personnelle).
- Liste "Mes offres d'emploi" : réelle (`JobOfferRepository.fetchByEmployer`), limitée à 3 sur le dashboard, "Voir tout" → `EmployerOffersScreen` (liste complète, suppression d'offre via le menu "..."). Chaque carte (`EmployerOfferCard`, partagée) affiche le nombre réel de candidatures reçues (`fetchApplicantCountsByOffer`) et ouvre `OfferApplicantsScreen` (candidats de l'offre → `CandidateApplicationDetailScreen`).
- Liste "Candidats suggérés" (`_suggestedCandidates`) : **réelle, tous les candidats inscrits** (profil visible) via `AccountSearchRepository.fetchAllJobSeekers()`. Ceux dont le titre/compétences/localisation recoupent une offre publiée remontent en tête avec leur % de correspondance ; les autres suivent sans score. Carte tapable → `CandidateProfileViewScreen`. Preview de 6 sur le dashboard, "Voir tout" → `CandidateSearchScreen`.
- Carte conseil (`AdviceCard`, widget local à `lib/features/dashboard/presentation/widgets/`, distinct de l'ancien `core/widgets/advice_card.dart` supprimé) et navigation basse (`BottomNavigation`) — voir "Flux d'écrans" pour les 4 sous-écrans accessibles depuis le menu bas.

Espace Chercheur d'emploi — `lib/features/dashboard/presentation/pages/job_seeker_dashboard.dart` :
